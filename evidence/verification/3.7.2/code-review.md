## 业务、用量与维护

- **查询与扣次。** 核对共享结果、失败退款、跨账号结果、已保存选择和近期记录。付款恢复增加一次本地存储核对；仅发现待确认订单时才请求原单。清空校验放在用户打开和操作旧消息时，读取该用户的一条清空记录。没有给库存轮询或每次正常发信额外增加该读操作。
- **库存监控。** 业务云函数是共享模块的维护源，监控包按依赖生成。审查了租约、旧结果、未知库存、重试、重复发送、同毫秒新记录和限流。共享鉴权服务线上同时服务两款应用，不能用仓库里的单应用授权覆盖现网配置。
- **性能边界。** 采用已归档的每分钟 600 次预算配置运行本地模型；模拟上游响应，生产请求为 0。300 人查相同三家店，300 人拿全结果、合计 3 次上游请求；独立的 300 个目标也全部成功。900 个不同目标时，178 人拿全、1 人拿部分、121 人未成功。持续混合负载下，1,200 次手动查询成功 323 次、繁忙 877 次，1,200 次自动采集准入成功 1,080 次、繁忙 120 次。各场景会员净扣次均为 0。模型使用历史配置与本机调度；尤其其中持续有货复查设置为 0，不能据此声称线上已达到 3 秒复查或 300 人任意查询目标。[输入配置](../3.7.0/collector-capacity-input.json) · [复现工具](../../../tools/run-capacity-300.mjs)
- **演变与重复返工。** 回看近 30 个日历日（10 月 23 日至 11 月 21 日）建立的 4 条 PR。#7、#8 分别约 16 天、14 天后关闭，均未以各自 PR 合并；已合并的 #9、#10 从创建到合并分别约 21 小时 38 分、20 小时 1 分。时长包含等待，不能据此归因于构建慢。#10 特意按实际 HTTP 开始时间计算采集间隔，本轮保留。支付与提醒反复出现的问题是不同入口对同一状态各有一套判断；本版把清空判定放回数据层、把账号核对放在真实下单前，并用相反先后顺序的测试锁定行为。[#7](https://github.com/kirrrto/guoxiaoshao/pull/7) · [#8](https://github.com/kirrrto/guoxiaoshao/pull/8) · [#9](https://github.com/kirrrto/guoxiaoshao/pull/9) · [#10](https://github.com/kirrrto/guoxiaoshao/pull/10)
- **接手位置。** 页面行为从 `miniprogram/pages` 找入口，支付恢复在 `miniprogram/utils/member-payment.js`。API 的 `lib/services` 编排业务，`lib/repo` 负责并发写入和账号可见性，`lib/engine` 负责采集、投递与外部请求。改共享代码后从 API 端重建监控包并做一致性检查。当前版本指纹只在发布说明前言声明，历史上传回执继续对应原版本。

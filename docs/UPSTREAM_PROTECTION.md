# 手动查询与自动监测的共享保护

## 1.1.3 的请求规则

- 手动查询和定时监测在实际发起取货请求前，共用 `gxs_config/collector_budget_<北京时间日期>` 的分钟、每日预算。沿用现有配置 `collector.maxRequestsPerMinute`、`collector.maxRequestsPerDay`，缺省分别为 60、10000。一次门店批量请求算一次预算，覆盖其中所有 SKU。预算是全环境合计，不是每个用户各有一份。
- 配额在事务中预留。预留后进程终止、探测过期或失去采集租约时，为防重放超额不返还上游预算；因此统计可能保守高于实际网络请求。采集健康记录的 `requests` 仅统计确已发起并完成的请求。
- `query.maxRequestsPerUserMinute` 缺省为 6，按过去 60 秒的新实时查询计算；`query.maxConcurrentPerUser` 缺省为 1。会员实时查询不扣使用次数，但仍遵守这些服务保护。历史查询不占用取货接口预算。
- 相同查询 ID 的结果重放不重复扣次、不重复发起网络请求，也不重复计入账号请求窗口。不同 ID 也不能绕过同账号并发保护。任务中断后可在租约到期后恢复，旧执行者不能释放新执行者的锁。

## 暂停与恢复

`gxs_config/upstream_breaker` 保存 API 与监测共用的暂停状态。429、503 立即暂停，支持秒数和 HTTP 日期两种 `Retry-After`；其他失败在一分钟内累计五次暂停。默认冷却 30 秒，重复失败指数延长至 30 分钟，服务器要求更长的有效等待时间时取更长值。

冷却结束只允许一个持有 30 秒租约的探测请求。探测失败继续冷却，成功后恢复；旧请求、已过期探测或被接管探测的成功结果不能解除新的暂停状态。数据源请求仍不自动重试、不跟随重定向。

预算拒绝和主动暂停不是数据源观测，不写入最新状态和事件历史，更不会被记成“无货”。全量未获得有效结果返还本次使用次数；部分门店成功时保留既有按次收费规则并说明其他门店暂未成功。页面显示原因和服务端建议的重试时间。

## 数据源边界

当前适配器访问网站取货状态接口，该接口并非本项目取得授权的开放 API。2026-09-16 复核的 [Apple 网站使用条款](https://www.apple.com.cn/legal/internet-services/terms/site.html) 对自动访问、获取、监控网站内容和不合理负载有明确限制。现有代码、低频请求和有效响应均不构成授权或长期可用性保证。

发布及扩大监测规模前，需确认适用授权与数据使用条件，或改接获得许可的数据源。这里的工程保护不能替代该确认。项目没有加入代理轮换、身份伪装、验证码绕过等措施。可取货状态也不代表真实库存数量或门店内部补货时间。

线上原有定时频率保持每分钟，消息发送和支付仍按已有关闭状态执行。真实订阅消息需另行完成模板、服务端凭据和用户授权验证。

# 果小哨 v3.3.0 发布说明

2026-10-18 本地候选。已完成源码修改与本地验证；本轮未部署云函数、未修改线上数据库、未上传小程序、未提审或正式发布，未向真实用户发送消息。仅上传前端不能使新通知逻辑或年卡第 5 个配置在生产生效。

## 用户能感知的变化

- 新关注、恢复关注或补充授权时，若后台确认当前已有货，可收到一次「当前可取货」提醒；同一轮持续有货不反复耗次数。
- 小哨卡片突出库存、门店与观测时间。过期的有货记录保留为历史信息，不能显示成当前有货。检测结果会自动同步；「单独查询库存」移至展开的门店详情，作为带入原配置到查询页的可选操作。
- 关注页在前台自动读取新记录，返回页面或恢复网络时主动更新；显示页面读取时间与各门店实际检查时间。卡片取消重复的「提醒已就绪」格和逐门店过期长警告，微信授权与库存时效分开展示。
- 我的页先展示已生效套餐、实际名额和关注用量；年费会员为 **5 个配置 × 每配置 5 家门店**。月卡 4×4、周卡 3×3，价格、时长及续费规则不变。
- 提醒记录和测试收信有直接入口；测试展示「微信授权 → 提交微信 → 实际查收」。微信受理与用户确认收到严格分开。
- 公告区分后台最近状态与运营说明，已打开的页面也会自动隐藏到期内容；同一公告修改后会重新显示未读提醒。

## 核心修复与边界

### 通知交付

原来消息只由库存变化事件规划：事件规划后新增关注、恢复或补授权，即使持续有货也可能一直没有通知。新增 `current_available` 仅依赖已记录、新鲜、连续确认的有效库存，不伪造补货事件，不增加上游库存请求。

按用户、门店、商品和有货阶段持久化去重；历史记录清理、冷启动、重复关注和补授权不重复耗次。免打扰、会员、发送开关、授权和发送前库存复核继续生效。明确可恢复的发送失败退回预占次数并退避；结果未知不自动重发。删除/清空旧失败回执后重新发送会获得新的可见序号和展示时间，新收到消息可以正常打开。

批量退役过期未占次数通知，避免旧任务堵塞新通知。补发分页游标持久化，避免冷启动重复扫描前一批用户。后台新任务与旧状态变化事件共用现有发送队列和防重屏障。

### 年卡权益

既有有效年卡读时自动按 5×5 计算，无需逐用户改数据。服务端套餐展示、保存事务、监测及通知均使用实际权益。`annualExpiresAt` 区分年卡权益与后续较低档套餐时段；年卡到期或退款后，超额第 5 项保留但暂停，不能因续月卡而虚增年卡权益期限。

### 请求、JS 与页面

#### 关注页自动更新与检测延迟补充

原前端轮询依赖 `nextRunAt + 20 秒`，读取等待可达 80 秒；又先等待 `user.bootstrap`，该请求失败会直接跳过 `follow.list`。修复为前台正常等待上限 30 秒，账户与关注只读请求并行、仍按账户代际隔离后展示；失败退避，离线停止网络读取，恢复网络/返回页面立即读取。纯本地时钟在离线与重试等待时仍使旧结果按原 120 秒阈值过期，隐藏/卸载清理定时器。自动读取不会请求订阅权限、扣查询次数或直接查询苹果库存。

「1 家可取货」对应那家门店的有效检查时间，不能再配另一门店的旧时间。最近失败检查与上次有效结果使用独立时间；未知或缺时间不能制造新鲜库存。付费且有 42 次授权、全局服务运行而个人结果已延迟的场景会明确展示库存待更新。

提醒详情、买到反馈与打开回执按账号和本次读取隔离。返回关注页后，先确认身份再记录打开；身份读取失败时保留重试机会，旧账号的迟到回调不会覆盖新账号的卡片、暂停新账号关注或误记打开。

针对后续微信开发者工具截图，修复原生非 mini 按钮默认 184px 宽度覆盖门店详情行的问题。详情入口填满卡片，左右分别显示门店数和「详情与管理／收起详情」；折叠卡片不再将手动查询作为主操作。预览补入本机基础库 3.17.3 的相关默认样式，并通过旧选择器负对照确认能检出截图中的缩窄问题。

自动采样和手动查询均写入同一库存记录，自动更新不依赖手动查询。内存验证中，到货授权 0、断货授权 41 时，分别在通知开关开启／关闭下连续自动采样，关注页均从无货更新为有货，未发起手动查询、未调用发送器、未扣次数。授权次数只影响相应消息发送，不应使有效关注停止检测；这是本地链路验证，不能替代线上采样状态核验。

后台复现了通知队列阻塞检测：在受控模拟中，20 条待发通知、每次发送耗时 7 秒时，原定时任务的 35 秒全部用于发送，库存扫描为 0。修复让定时模式的采样与单条串行发送链并行，仍受同一租约、请求预算、发送前检查和函数时间边界约束。函数退出前等待已发起的发送收尾。具体回归证据见本次延迟专项测试。

这些修复不等于生产延迟保证。以默认每日持续请求目标 10,000、自动检测占比 80% 为例，17 个合并目标组的正常周期至少约 184 秒；按分钟触发时还会向上对齐，可能约 4 分钟。需用线上合并组数、实际预算、`collector.intervalMs`、定时触发与请求限流记录确认实际瓶颈；本轮不擅自提高上游请求预算，也不放宽库存新鲜度阈值。

维护者确认：2026-10-16 14:00 发布的「接口限流说明」已于当日 **20:20（北京时间）**结束。前后端为这一条缺少截止时间的历史公告补齐有效期，过期后公告列表、查询公告和未读红点均不再展示；不会屏蔽之后同名的新公告，也不会据此宣称当前接口已经恢复。后台公告筛选同时修正为使用请求时钟，避免列表与横幅使用不同时间。

本地兼容修复随代码部署生效。若要让现有线上版本立即下架这条旧公告，需在运营工具读取最新运行配置，找到标题和发布时间都匹配的原记录，仅将其 `expiresAt` 补为 `2026-10-16T20:20:00+08:00` 后按当前 revision 保存，保留其他公告。本轮没有写入线上运行配置。

同条件只读请求合并、离线快速失败。本地 12 秒读取截止后不再自动重发尚未返回的原生请求，避免原先两轮最坏约 24.8 秒等待；已明确返回的网络失败保留一次安全重试。写操作维持原幂等与恢复机制。这是本地等待策略改进，不是线上响应时间承诺。

已复现并修复选择器父层回写事件循环、配置弹层跨组件 observer 重入、日志处理再次触发日志的递归。查询、历史、我的和小哨增加迟到响应及账号切换保护，避免旧账户状态或成功提示覆盖新账户。查询进度区分慢请求、缓存与本次结果；历史返回只更新时效相关字段。

截图中的 `-601008`、`Maximum call stack size exceeded` 和 `FLOW_UPDATE` 没有业务源码栈，不能仅据运行时栈确认线上根因。上述缺陷有本地复现和回归；线上超时原因、实际启动/跳页/刷新延迟、iOS/Android 基础库渲染及错误率需对应日志、Source Map 和设备证据。

## 上线顺序

1. 保留当前云函数代码和运行配置备份。按 `config/database-deployment-plan.json` 补缺失索引，重点新增 `gxs_notifications.status_detected_reserved`（`status`, `detectedAt`, `subscriptionReserved`）；不删除现有索引，不覆盖线上凭据、发送开关或支付配置。
2. `node tools/build-monitor.mjs` 后同步部署 **gxs_api / gxs_monitor**（及按当前发布目标对齐的 cloudbase_auth）；确认实际部署包、版本探针、定时触发和共享环境匹配。
3. 在批准的测试账号上核验：新关注时持续有货、补授权后仍有货、同轮不重复扣次、到货后断货再补货、免打扰、过期/未知库存、明确失败重试、结果未知不重发、删除旧失败回执后新消息可打开。
4. 使用已有年费账号保存第 5 个配置，核对服务端采集与提醒也覆盖它；月卡仍为 4 个。核验到期/退款后的保留与暂停行为。
5. iOS 与 Android 真机试收实际微信消息并由本人确认；核对通知中的配置、门店、发现时间和点开详情。微信受理日志不能代替手机收件记录。
6. 至少连续观察真实定时触发、各活跃目标最后观测时间、最旧待发任务、失败/结果未知比例和实际延迟。用新版本业务栈/Source Map 复核截图中的三类 JS 错误。
7. 以上通过后再上传 v3.3.0、体验验收、提审与发布。发布说明只保留已登记的 3 句用户变化，不提前宣称上线验收完成。

## 回退

保留原版函数和小程序包；若通知出现异常增长，优先通过现有运维开关暂停发送并保留用户配置与额度，核对待发/结果未知任务，不手工重放结果未知消息。代码回退需同步 API 与 monitor；新增索引可保留。回退至旧版权益逻辑会暂时限制第 5 个配置，需明确告知测试/运营人员，不能删除用户配置。

## 2. 本次取舍与需求追踪

维护者补充说明：项目书与效果图都是参考，不要求原封不动照搬。本次沿用已有真实业务能力与四个底部入口，优先解决查询目标、提醒管理、跨页回程和多段免打扰；没有按示意图另建“查询记录/提醒记录混合历史”，也没有为了新版加入新商城、资讯流或额外主导航。

本次的主要取舍：查询页把主动打开的日历与攻略入口放在品牌标题后、配置选择前，结果主操作放在门店列表之前；有新鲜可取货观测时优先呈现对应门店并帮助用户在官方渠道下单。选择器直接形成有效草稿，在底部一次保存。小哨用紧凑卡片展示关注，明细在同页展开；“我的”和小哨都可直接补充微信提醒次数，反馈及原请求重试留在原页。历史保留真实供应变化记录，当前观测和个人提醒记录各自独立。指南按入口区分海报与攻略，不自动弹出宣传海报。

以下覆盖项目书 15 个需求组、共 51 个编号，登记本地实现/复用/待验的边界，不是 51 项验收签收表。

## 3. 维护者补充需求：多个免打扰时段

本次增加 1–8 个时段的添加、编辑和删除，保留总开关。时间均按北京时间解释；例如 `23:00–08:00` 表示跨至次日。起止相同沿用既有“全天”语义，页面明确标出；有重叠时取并集。每段采用开始时刻包含、结束时刻不包含的区间。

在项目书基础上增加两项便捷操作：一键添加“夜间 23:00–08:00”或“午休 12:00–13:00”，之后仍可自行改时段；状态摘要显示当前是否免打扰，以及按合并时段计算的恢复时间。只有用户主动点击才写入快捷时段，并保留当前总开关选择。

新结构为 `settings.dnd.periods = [{ startMinute, endMinute }, ...]`；每个分钟值必须是 0–1439 的整数。保留顶层 `startMinute/endMinute` 为第一段的兼容镜像。旧账户仅有单段时继续正常读取，无需批量迁移用户数据。`enabled=false` 保留时段设置但不拦截通知。

实际涉及：

- 前端展示/就绪判断：`miniprogram/utils/dnd.js`、`utils/reminder-readiness.js`、`pages/mine/`。
- 参数校验：`cloudfunctions/gxs_api/lib/services/users.js`、`lib/rules/dnd.js`。
- 原子写入保护：`cloudfunctions/gxs_api/lib/repo/atomic-ops.js`。当前账号已存在超过一段时，旧客户端只提交单段字段会返回 `dnd_client_outdated`，不会丢掉其余时段；此保护位于事务内，避免并发旧请求覆盖。
- 发送判断：`cloudfunctions/gxs_api/lib/engine/notifier.js` 在任务规划与实际发送前共用规则；当前处于免打扰或事件发生于免打扰时段都会抑制，避免结束后补发旧变化。后台观测继续，免打扰与暂停关注不是同一概念。
- 派生监测包：`gxs_monitor` 必须通过 `node tools/build-monitor.mjs` 从当前共享源码生成，并经 `--check` 核对。

### 必须遵守的部署次序

以下是候选发布方案，**没有执行生产部署**。

1. 先保存线上 `gxs_api`、`gxs_monitor` 的完整代码包、配置及触发器摘要，取得前端/后端版本映射和回退依据；不在文档记录密钥或签名 URL。
2. 完成同一源码版本的构建与本地检查。先部署能够读取单段和多段的 **`gxs_monitor`**，回读确认其代码一致及原定时触发器保留。此时旧用户单段设置仍兼容。
3. 再部署同版 **`gxs_api`**，回读确认参数校验、事务保护和发送路径都识别 `periods`。只有两端均已核实一致，才允许新前端保存多段。
4. 最后预览/上传 v3 前端并执行真实账号设置回读、端侧展示与有授权的提醒验证。真实发消息、付款、退款、生产变更需要对应明确授权，不由本交接文档自动触发。

不可仅上传 v3 前端配旧 API：旧端可能只保存第一段，不能把客户端显示视为保存成功。也不可只更新 API、长期保留旧 monitor：旧发送器无法保证拦截第二至第八段。前端回退到旧单段 UI 后，多段用户需保留新版服务端保护并提示更新；不能通过清掉 `periods` 让旧 UI “可用”。

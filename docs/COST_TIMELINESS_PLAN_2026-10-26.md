## 后续架构实施顺序（常驻改造尚未实施）

1. **延长一分钟实测。** 按相同活跃目标数、采样数和时间长度比较 DB/API 次数、事务冲突、样本年龄与通知等待。区分每次采样成本和全天总量，避免用暂停监测制造节省。
2. **验证最小常驻进程。** 以 [runner.js](../tools/collector/runner.js) 为起点，先本地回放、压测，再评估单实例。仅搬迁进程不能消除逐轮数据库调用。持续采样由独占租约及递增执行代次约束；SCF 保留接管入口，旧实例失权后不得持久化或发送。
3. **分开即时事件与稳定摘要。** 热状态按 target、执行代次、样本序号有序更新；状态变化、unknown 中断、确认样本与 outbox 必须即时可靠落盘。稳定样本按有界窗口合并摘要，携带序号范围和幂等键，保留跨日计数、观测时间及确认链。重启只恢复持久化进度，缺失区间明确记录，禁止补造或重复累计。先验证真实服务端事务契约，不能假定 `Promise.all` 可在共享事务内并发；缓存与 outbox 分离设计也须验证故障一致性。
4. **同步改造读取与授权。** 实时 API 经鉴权读取可信热状态，并校验代次、观测时间；热服务失联时回退持久快照并标明陈旧，沿用受控手工刷新。不能只减少 latest 写入，让现有新鲜度判定失效。付款生效、关注变化、新授权及撤销须触发失效/可靠增量通知，并有短周期补偿扫描；发送前重新检查会员、关注、额度与目标状态，旧缓存不得漏掉新付费或新授权用户。

## 预算与规格

设一次完整覆盖需 G 个上游请求、周期为 P 秒、自动份额 a，则上游日请求约为 `G×86400/P`，总预算至少 `G×86400/(P×a)`；另留手工、失败重试和突发余量。21 组、P=3、a=0.8 时分别为 604800 和 756000 次/日。并发容量还须满足请求耗时及同店间隔，增加预算不保证达到该周期。

[官方规格](https://docs.cloudbase.net/run/deploy/configuring/resources/cpu-limits)最低为 0.25 核/0.5 GiB。[上海资源点价格](https://cloud.tencent.com/document/product/876/127357)列出 CPU 0.055 元/核时、内存 0.032 元/GiB时；单实例运行 720 小时计算资源约 `720×(0.25×0.055+0.5×0.032)=21.42` 元。文档库调用 0.2 元/万次、云开发 API 0.1 元/万次，应按各自实际计费量核算。此为公开标价模型，不是总账单：还含网络、日志、存储及套餐抵扣，实际环境计费口径须先核实。

## 验收与回退门槛

- 一分钟阶段：同负载下 DB/API 单样本成本下降，样本年龄和确认后发送等待的 P95/P99 不劣于基线，覆盖目标不减少。
- 秒级阶段：先定义候选周期和容量上限，记录至少 24 小时覆盖、确认、发送延迟；通过双实例竞争、崩溃、断网、跨日、429、乱序、重复及付款/授权并发测试。事件不得丢失，重放不得重复扣额度或发送。
- 接管验证必须覆盖“事件已落盘但未发送”与“摘要尚未提交”；超出持久化能力时施加背压并明确陈旧，不静默丢样本。任一正确性门槛失败即停止迁移，恢复现有一分钟路径及持久 outbox。新增资源实施前核对规格、费用和回滚方案。

# 1.5.1 容量与检测频率验收

要求确认于 2026-10-01：至少 300 人同时点击查询，全部有效关注目标每 60 秒完成一轮检测，发现有货后每 3 秒复查取货状态。机器可读要求在 `config/delivery-targets.json`。这些是交付标准，**当前尚未全部达到，正式发布受此阻断**。

“库存”在本项目中指门店是否支持取货，不是剩余件数。数据适配器解析 `pickupDisplay`，没有可核验的库存件数。页面读取已有状态与后台发起真实采集是两件事；当前页面可见时约每分钟读取，不承诺页面每 3 秒自动刷新。

## 原逻辑与差距

1. 每名会员最多三个关注配置，每个配置最多三家门店。后端按门店与商品去重，同店每 20 个商品分一组，请求一次可取得这一组的状态。
2. 原定时器每分钟启动一次，但不意味着每组每分钟成功采集。18 组在当前持续容量下规划 194.4 秒，再按分钟对齐，约四分钟轮转。
3. 原加速只在状态变化后维持约 20 秒；即使一直有货，状态不再变化也会退出。持续有货复查需要单独的状态及配置，不能只把原 `burstIntervalSeconds` 改成 3。
4. 定时云函数每次最多运行 55 秒，平台剩余时间接口失效时用 35 秒后备值。与每分钟触发之间存在空档，单靠该部署方式不能保证连续每 3 秒采集。需要已有常驻 collector 的部署及实际运行验收。
5. 所有采集仍要尊重上游响应、同店间隔、容量和真实 429/503 退避。过期、未知、持久化失败的样本不能当成成功检测；收到繁忙也不算容量验收成功。

## 容量下界

以下按 18 个去重请求组计算，不是 18 位用户；同店超过 20 个商品会继续增加分组。

| 工作量 | 自动新 HTTP 需求 | 按自动占持续补充 80% 计算的全站速率目标 |
|---|---:|---:|
| 全部组每 60 秒一次 | 18/分钟，25920/日 | 至少 32400/日 |
| 全部组有货、每 3 秒一次 | 360/分钟，518400/日 | 至少 648000/日 |

这是理论下界，没有含失败复查、通知、数据库事务和突发手动查询余量。当前默认全站持续目标 10000/日、分钟上限 60；配置校验当前也不允许超过 100000/日。因此不能通过填一个未经验证的数字来启用上述承诺。单个组每 3 秒已约需 28800 次/日自动请求。

吞吐还受单次响应与并发影响。6 个新 HTTP/秒、平均请求用时 2.5 秒，仅网络在途数下界就为 15；当前默认并发为 2，配置上限 10。同店串行和间隔保护会进一步影响同店多分组轮转。审查已复现原通知发送等待阻塞采集，本候选在新常驻有货模式下隔离了该等待，仍需用完整业务路径测量数据库、网络与发送竞争，不能只计算网络请求数。

300 名会员查询同一热点可复用一份新结果；300 个不同目标需要更多采集。离线验收同热点全部成功，300 个独立目标只有 59 人完整成功；900 个独立目标为 19 人完整成功、1 人部分成功、280 人繁忙。细节及模拟边界见 [审查记录](AUDIT_1.5.1.md)。这些结果明确证明当前配置没有达到最坏目标分布的即时容量。

## 实施与验收顺序

1. 以常驻 collector 为连续采集执行器，验证不会缩容到零、失联可恢复、全局租约保证单一所有者；定时 monitor 作为受同一租约约束的后备。仅部署常驻进程仍不等于已达到频率。
2. 使用候选新增的持续有货调度能力。正常周期设为 60 秒，有货复查目标为 3 秒；只有真实持久化的有效状态才能维持快速复查，未知或失败不能伪造新样本。源码默认关闭该新增加速，避免更新代码时无意扩大生产请求量；开启须与容量验收一起进行。
3. 按真实有效关注目标分布、同店分组、热门查询命中率确定所需采集量。验证上游可承受的请求率、超时与限流，再决定可用数据源和容量；在此之前保留所有保护。
4. 为 300 个不同目标减少重复采集工作，评估批量共享及预采集。跨实例批量调度必须同时验证目标租约、原子持久化、免费次数补偿、事件确认及部分结果，不用单进程内存合并假装具备云端能力。
5. 在隔离云端运行真实数据库、与生产匹配的函数配置和 SDK，测量 300 人热点、300 个不同目标、每人三店、上游慢响应及前后台同时竞争。分别记录完整成功、部分成功、繁忙、错误、响应分位数、真实 HTTP 数和净扣次。
6. 持续记录所有关注组相邻成功观测间隔及覆盖率，包含长期有货超过 20 秒、无货恢复常规、冷启动、租约交接、同店多分组、跨北京时间午夜、真实限流与恢复。一分钟全覆盖和有货三秒复查分别判定，不能由心跳、平均值或单个热点通过来代替。
7. 验证观测停滞告警实际送达与恢复；用真实手机核对付款到账后立即使用和授权后的提醒送达。达到以上标准后再部署发布候选、上传前端、提交审核。

截至本候选准备阶段，未部署常驻生产实例、未提高生产请求速率、未执行生产压测、未证明上述频率。后续运行证据须与确切 Git 提交和实际下载包绑定。

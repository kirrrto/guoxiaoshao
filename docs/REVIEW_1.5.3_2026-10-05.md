# 1.5.3 稳定性与新用户体验审查

日期：2026-10-05（北京时间）。在原 1.5.2 未提交修改上增量修复，并按维护者确认准备 1.5.3 发布，保留会员专属持续关注／真实提醒，按用户确认新增有限次数测试通知与 30 天/365 天套餐。本记录描述本地候选，不表示云端已部署或小程序已发布。

## 超时与连接恢复

- 用户提供的 `-601008 server-side request timedout` 只有 `WACloud.js`／`WAServiceMainContext.js` 帧，无法据此确定具体接口、请求阶段或服务端根因。
- `onError` 与 `onUnhandledRejection` 现在共同识别明确的、只有 SDK 帧的超时，记录 `[gxs] sdk_timeout` 警告。业务帧、混合栈、未知异常及缺少栈的错误仍保留 error。该处理只改变自定义实时日志，不保证微信平台自身异常统计不再记录，也不会消除真实超时。
- 原有安全读只重试一次；查询、保存、支付等写操作不因这次修改而自动重复。
- 账户的非关键 `lastSeenAt` 写入失败不再让已完成的会员、余额、身份读取一起失败。保留十分钟写入节流，后续访问重试；必需账户与配置读取仍严格报错。
- 「我的／小哨」首次连接失败后返回页面可恢复。关注列表未确认前显示加载状态，避免把失败当成没有关注。
- 已同意的提醒授权在同步超时后明确显示待同步；按原请求编号补同步，不再催用户重复授权。相同余额的确认也能清除待同步状态。

定位线上超时应对照 `[gxs] api_failure` 的 `action`、`phase`、`attempt`、`durationMs`、`errCode`、`requestId` 和发生时间。初始化阶段再核对共享环境授权函数；业务调用阶段核对对应 API 与数据库耗时。

## 查询次数一致性

- 本地存储不可用时，同一运行期用内存保留未确认的查询编号。回归模拟服务端已扣次、响应丢失、共享缓存过期后重试，确认只执行一次新采集、只扣一次。
- 操作完成后保留内存完成标记，避免清理存储失败后重新使用旧编号；旧请求晚到不能清理新目标编号。
- 存储写入失败且应用彻底重启时，无法恢复未保存的请求编号。这一边界仍存在。
- 重放查询返回当前账户余额，保留原结果、采集时间和本次收费信息。查询余额携带同一事务读取的修订号，前端按修订号处理与签到／任务奖励交错的响应，避免旧余额覆盖新余额。

## 首次使用与分享

- 免费账户没有查询次数时，可在首页主动签到领取，保留已选择的配置与门店。不会自动签到或自动发起收费查询；签到失败可以原地重试。
- 同页签到与查询互斥，旧余额响应不覆盖更新状态。
- 查询页的朋友分享携带公开的商品编号和门店编号，不带账户、余额或库存快照。打开链接后检查当前目录，恢复到对应配置；点击查询后才获取结果。
- 分享支持冷启动和已有页面热启动。目录尚未更新时保留分享目标；正在编辑或查询时通过明确按钮稍后载入，避免覆盖正在进行的操作。原有本地选择不被分享链接自动改写。
- 提醒次数建议去重；服务异常或已有授权待同步时优先给出恢复操作。

## 用户确认后的功能补充

- 不额外赠送首次查询。签到/任务的有限次数可主动体验【测试】通知，每条扣 1 次，会员亦然；明确未发送或微信拒绝时退回，超时未知保留原记录与扣次，不盲目重发。收到/未收到反馈独立于微信受理状态，旧消息落地不会清掉另一条待处理测试。
- 新增 30 天 ¥19.90（`vip777`）、365 天 ¥200（`vip888`），保留 7 天 ¥7（`vip666`），均不自动续费；用户提供的截图显示三种道具已发布。已购会员可升级长期套餐或续费，按全价支付、原余期顺延、不抵扣差价，不伪造会员等级。原订单快照、跨重启套餐绑定、叠加续期与按单退款已覆盖；购买弹窗后账户/订单变化或服务端纠正套餐时必须重新确认，不能把旧确认用于新订单。
- 修正到货有授权但断货无授权的就绪状态；断货可选，不再单独因为未授权断货反复提示。
- 已补齐「这些颜色或门店我也接受」：本人有效付费或会员查询后，主动勾选同型号、同容量且其他配置一致的颜色及附近／同城门店，读取已有 120 秒内可取货观测。服务端核验原查询归属、净扣次／会员凭据和不可延长的窗口；配置、门店各最多 3 项，每次最多读取 9 个目标。只用目录坐标计算距原门店的距离，缺坐标时明确标为同城、未计算距离，不使用用户定位。应用前再次只读核验，切页或更改选择后的迟到响应不覆盖条件；不会额外采集、扣次或添加关注。未知、过期、未来和异常时间样本不展示，无观测不等同于没货。
- 历史增加单日真实记录与采样覆盖摘要，不把单日记录宣传成 7 日预测。
- 管理后台区分正式提醒与测试统计，展示去重行为人数、详情查看和买到反馈；这些指标不是严格逐级漏斗，也不是已证明的留存增长。
- 新增 `gxs_notification_tests` 的服务端集合/索引；两项新道具映射与启用补丁已备好，尚未部署或应用到云端。详细配置与验收见 [发布说明](RELEASE_1.5.3.md) 和 [支付配置](VIRTUAL_PAYMENT_SETUP.md)。

## 增长后的容量边界（离线结果）

使用现有 `tools/run-capacity-300.mjs` 对当前候选进行离线测试，未修改生产预算或取消限流保护：

| 场景 | 完整成功 | 部分成功 | 繁忙 | 模拟新上游请求 |
| --- | ---: | ---: | ---: | ---: |
| 300 人同时查同一目标 | 300 | 0 | 0 | 1 |
| 300 人同时查同一组三店 | 300 | 0 | 0 | 3 |
| 300 人分别查询不同目标 | 59 | 0 | 241 | 59 |
| 300 人各查询三个不同目标 | 19 | 1 | 280 | 59 |

这些是内存仓库和模拟上游结果，不证明真实云端吞吐或手机响应时间。默认持续容量为全站每日 10000 次对应的补充速率，约 6.94 次／分钟；自动采集份额约 5.56 次／分钟。用户数相同但去重后的门店／商品目标更多时，更新会变慢。完整容量讨论延续 [容量验收](CAPACITY_ACCEPTANCE_1.5.1.md)，不能宣传所有目标每分钟更新或持续三秒复查已达标。

留存工作的下一阶段应核对真实首次查询完成率、繁忙占比、成功观测间隔及提醒发送失败原因；在已有合法统计范围内比较同口径的新旧版本。当前没有可证明留存增长的线上数据；本版增加本账号测试收件反馈、正式提醒详情首次查看及服务器已有记录的去重行为统计，不接入第三方追踪。扩容需根据真实去重目标分布、上游允许的速率和云端压测决定，不能只调高预算数字。

# 1.5.1 全面代码审查与验收记录

日期：2026-10-01。目标：修复确认可复现的业务使用故障，准备 1.5.1 发布候选；用户确认的交付标准为至少 300 人同时查询、关注每 60 秒检测一轮、有货每 3 秒复查状态。此记录不会保证软件绝无缺陷，也不把离线测试写成线上、支付或消息送达证明。

## 审查范围

| 范围 | 核对内容 |
|---|---|
| 身份和权限 | 消费者/资源方身份配对、管理员鉴权、普通请求和 HTTP 支付入口隔离、跨账号订单/关注/通知访问。 |
| 支付与会员 | 权威查单、签名和回调、重复请求、到账幂等、续费、到期、部分/全额退款、兑换、权益账本。 |
| 查询与次数 | 真实查询入口、日额度迁移、共享容量、会员扣次、并发与重放、超时补偿、目标复用及租约。 |
| 数据与历史 | 原始库存语义、未知/未来/旧观测、持久化事务、分页快照、无结果退款、关注状态及历史保留。 |
| 巡检与提醒 | 调度恢复、动态周期、跨日容量、连续确认、任务去重、发送时重新校验、授权预占/退回、不确定发送和实际观测健康。 |
| 消费者前端 | Query/Follow/History/Mine、支付兑换后刷新、缓存失效、异步竞态、请求编号、页面销毁、弱网恢复、提示与权益文案。 |
| 运营及部署 | 旧配置覆盖、服务端原子校验、生成 monitor、版本及锁文件、依赖包边界、CI、下载内容比对。 |
| 工具与依赖 | 常驻采集、目录同步、数据库/云函数权限计划、SDK入口、本地HTTP兼容验证与 npm安全公告。 |

多人分别审查并进行跨领域复核，先用失败用例确认问题，再修代码。三方 SDK 的审查为依赖公告、使用路径和兼容性验证，不声称人工逐行证明所有第三方代码安全。真实部署权限与数据库规则仍需控制面核验。

## 关键修复及复现证据

1. **支付成功被清理异常覆盖。** 注入订单租约释放失败，原实现已到账仍返回待确认；修复保留原成功或明确拒绝，按原 TTL 恢复并发保护。`virtual-payment-service` 回归另串起零积分 → 付款确认 → 查询 → 续费 → 到期 → 旧凭证重放 → 新购恢复。
2. **查询成功被目标清理异常覆盖。** 成功样本已落库时释放租约失败，原实现错误退款并显示失败；现在保留真实结果，已有样本仍可共享，真实失败继续退次。首个 429/503 的暂停时间也明确返回。
3. **300 人共享慢响应时提前失败。** 正常上游用时 2.5 秒，原 1.4 秒等待使 299/300 返回刷新中。现最多九次有界准入读取，等待受原查询截止时间限制，不追加采集请求、不伪造样本确认。
4. **在途消息许可被旧池修复复制。** 两次许可在发送中时，旧修复只统计 accepted 而再次发行两次。现在 union 统计已发送/已占用/不确定且未退回的许可，事务核对账本快照并有界重读，历史记录缺失不能复活已使用票。
5. **旧页面删除新操作重试 ID。** `operation.finish` 必须与本次 ID 匹配，网络不确定时保留原 ID；跨页晚响应不再引发新的扣费请求编号。
6. **旧缓存覆盖新会员状态。** 支付/兑换/保存使缓存失效后，旧成功和旧失败响应不覆盖新数据。页面销毁后仍确认已成功的业务操作，但不更新旧 UI 或污染新结果缓存。
7. **历史页残留免费权限拒绝。** 会员生效只清除能被权益解除的旧限制；过期会员收到服务端拒绝时也刷新账户。真实上游暂停不被会员标识隐藏。
8. **已失效提醒仍发送。** 发送前及预占授权后重新核对库存、会员、关注、开关和时效；最后一次异步续租必须先于最终状态读取，明确未发送时退还许可。
9. **任务租约过期仍可能外发。** 实际发送与超时受任务自身租约和工作时限双重约束，不把 uncertain 重置为 pending 重发。
10. **心跳掩盖业务停滞。** 每组跟踪成功且持久化的观测，跨冷启动保存新目标宽限和实际成功时间；失效写入不能刷新健康状态。未来 checkpoint 以可信恢复时刻重建监测起点，但不伪造成功时间或清除真实 Retry-After；超过停滞阈值不再永久显示预热。聚合结构化日志供平台告警规则使用，前端显示更新延迟。
11. **未来时间库存被当作当前状态。** 关注和历史返回未知；写入时以服务端可信时钟识别明显未来污染，新观测可修复旧污染但不能伪造补货事件和连续确认。新输入超过 30 秒容差直接拒绝，正常乱序仍不覆盖较新样本。事务失败不得留下部分修复，未落库的观测不得算作采集成功；发送前拒绝未来库存。
12. **旧运营配置覆盖已修复容量。** 运营编辑器携带读取时版本，事务拒绝陈旧保存，保留编辑内容并提示刷新，避免保存公告时把 continuous 写回 daily。服务端同时拒绝普通管理员无版本的旧客户端；可信 SDK 上下文认定的云端运维脚本保留兼容，不能由请求体伪造此例外。
13. **同版本旧云包蒙混验收。** 增加下载包源码哈希核验，检查旧内容、缺失函数和额外旧运行文件，版本号相同仍可失败。
14. **持续有货时仍退出加速。** 原加速只看状态变化后的二十秒窗口；新增显式 `availableIntervalSeconds`，有货状态已持久化后可持续复查，未知和写入失败不构成有货证明。配置启停和冷启动保留真实等待与失败保护。默认 0 不擅自增加生产请求量，设为 3 的本地调度回归不能替代真实三秒覆盖验收。
15. **慢消息阻塞持续有货采集。** 新常驻有货模式将通知发送与采集等待分开，发送仍串行，重复唤醒合并为单个在途工作和一个待处理标志。慢发送期间采样仍可完成；停止须等待已开始的发送结束，失去租约后不再启动后续发送或采集。默认关闭新模式与定时采集维持原生命周期；数据库和上游延迟仍需实测。

## 容量结论

300 人同时点击是用户确定的目标，不是已完成的承诺。同目标的成功可以复用一次实际采集；不同目标仍受真实请求预算约束。专项工具为 `node tools/run-capacity-300.mjs`，使用真实业务处理器、300 个模拟独立会员身份、内存事务和明确模拟的上游；绝不把它描述为真实云压测。

旧参数的全站持续能力为约 6.94 次新上游请求/分钟，手动份额约 1.39 次/分钟，可积存、共享和有界借用。默认 18 个自动组规划 194.4 秒，分钟定时对齐后约 4 分钟轮转。多SKU批处理、共享预采集和数据源扩容需要另以真实目标分布、时效、上游承载、云数据库事务争用与成本验证；不能关闭保护来冒充达成 300 并发。

| 300 个独立会员上下文 | 完整成功 | 部分成功 | 繁忙 | 模拟 HTTP 数 |
|---|---:|---:|---:|---:|
| 同一门店与商品，快速响应 | 300 | 0 | 0 | 1 |
| 同一门店与商品，上游 2.5 秒 | 300 | 0 | 0 | 1 |
| 同一商品，共同查询三家门店 | 300 | 0 | 0 | 3 |
| 300 个不同商品，各查一家门店 | 59 | 0 | 241 | 59 |
| 300 个不同商品，各查三家门店 | 19 | 1 | 280 | 59 |

所有场景会员净扣次为 0，同一波没有重复目标采集；慢响应仅形成 1 份样本，299 人共享，不将读取误算为库存二次确认。修复前同一慢目标仅 1 人成功、299 人过早返回刷新中。

混合竞争另模拟四轮各 300 个手动查询与 300 个自动准入，每轮推进 45 秒，跨北京时间午夜并重建 handler。135 秒内总计 75 次模拟 HTTP，未突破连续补充包络 75.625、分钟上限或产生负 token；手动仅 4 次成功，其余 1196 次繁忙，自动 71 次成功。这证明守恒及跨日保护，不证明超额负载可接受，也不是实际调度流量预测。

按现有每个门店与商品一请求的手动实现，300 个独立目标在 14 秒内全部取得新结果，至少需要 21.43 次新 HTTP/秒；900 个独立目标至少 64.29 次/秒，尚未计真实网络和持久化耗时。当前持续补充仅 0.11574 次/秒，分钟硬上限也不允许该负载。不能把局部热点的去重结果当成最坏负载验收通过。

不同目标的 300 人即时成功验收是发布阻断项；后续真实验收须记录全成功、部分成功、繁忙、HTTP 数、响应分位数及每组观测新鲜度，不将返回“稍后再试”算作成功。内存事务复制开销也不能当成云端性能指标。

新增频率标准同样尚未达标：原有货加速 20 秒后退出，分钟云函数具有运行空档，当前容量不足以支持 18 组每分钟或全有货时每 3 秒采集。精确容量下界、所需常驻执行和验收标准见 [容量与检测频率验收](CAPACITY_ACCEPTANCE_1.5.1.md)。

## 依赖安全审查

保留腾讯 `wx-server-sdk 4.0.2`，npm registry 核实其仍是当前发布版本。其固定依赖 axios 0.27.2 及 lodash.unset 4.5.2 命中公告，候选通过 overrides 固定为 axios 0.34.0、lodash.unset 4.18.0，同步四个部署包的 lock。SDK 的 metadata 和扩展 GET/POST/PUT/DELETE 仅对本机假服务做兼容验证，没有访问真实 metadata 服务或凭证。

- [Axios 0.34.0 官方发布说明](https://github.com/axios/axios/releases/tag/v0.34.0) 记录请求配置和代理相关加固。生产网络/代理配置仍需候选部署核验。
- 审计剩余 4 个 high 包条目均沿同一个 `lodash.set 4.3.2` 根因传播（database、node-sdk、wx-server-sdk），并非四个独立漏洞。[公开公告](https://github.com/advisories/GHSA-p6mc-m468-83gw) 列出该独立包无已修复版本。
- 已核对该调用位于 CloudBase 数据库 realtime `watch` 更新字段路径，当前项目不调用 SDK watch；当前业务中未确认可达利用路径。这不等于依赖零风险，不能删掉审计结果，也不能为了扫描清零而降级 SDK 或未经验证替换数据库核心。
- 本地安装中发现过 npm 包内误入 `file:../..` 自引用；已移除并补发布检查拒绝所有本地链接依赖，最终包必须可独立安装。

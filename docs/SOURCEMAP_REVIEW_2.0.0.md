## 此次发现的通知测试遗漏

映射里的 `pages/notification-test/index.js` 比改动前本地文件多出账户绑定、迟到响应隔离及权限提示。本轮首次交付没有整页复制这份代码，但也没有补齐其中必要的账户隔离。

离线复现的前端路径：A 允许原生订阅，保存授权失败；随后页面切换到 B。原本地页面更换了 `storageKey`，却保留 A 的内存 `pending`，B 仍能看到并执行“继续原测试”。在模拟后端中，这会使用 B 的通知测试额度。对照映射里的页面，相同状态切换会清理当前页旧账户操作状态。

进一步用映射页面与本地真实服务代码组合复现：页面传了 `expectedUserKey`，但服务的 status/authorize/send/feedback 没有校验该字段。即使页面做了绑定，原生提示等待期间服务端身份改变，仍可能按新的可信身份处理旧页面意图。因此只复制映射前端并不足以闭合这一边界。

此次修复采用两层一致性检查：页面将待测试意向和异步响应绑定到发起账户；服务端将可选 `expectedUserKey` 与 SDK 提供的可信身份核对，在不匹配时拒绝。客户端字段不能选择操作其他账户。旧客户端未提供字段时保留原兼容行为；新的客户端携带该字段，服务端写响应返回实际所属账户供页面核验。具体通过数以最终验证汇总为准。

所有通知复现使用本地运行器、内存仓库和模拟发送器，没有发送真实订阅消息，没有改动生产账户、真实额度或生产开关。

发布时须先部署包含一致性守卫的 `gxs_api`，再验收更新后的客户端；只复制映射前端或只更新页面不足以验证完整链路。原生授权期间确认账户变化时，新返回的授权结果丢弃，不自动绑定另一账户或重试发送；此前已确认属于原账户的未完成编号仍可在回到原账户后恢复。

## 仍需异常详情才能定位的内容

Source map 保存的是源码及编译位置映射，没有逐次错误发生记录。要把某条线上 JS 异常还原到原始行列，仍需该条错误消息、压缩文件的行号/列号或完整堆栈，以及对应版本。机型、基础库版本与触发操作有助于复现，但不能用当前源码推测不存在的错误详情。

本轮结论是具体源码路径及可复现行为，不是“9 个 map 等于 9 个报错”，也不声称这些模拟条件已经在线上发生。

# 1.1.0：玻璃界面与后台补货监测

更新：2026-09-16。

## 此前为什么收不到自动提醒

线上关注记录处于 `active`，但云端没有本项目的常驻采集服务或定时采集入口；runtime 沿用采集关闭、消息关闭、模板为空的默认配置。前端只会在可见时每 15 秒读取数据库已有观测。

旧界面将“配置已开启”和“后台服务未运行”合并成“已关注，等待启动”，同时又显示“暂停”，因此让用户误以为自己没有开启。这是产品状态表达和后台运行交付都不完整造成的。

## 现在的界面

查询、关注、历史、我的，以及产品/门店选择器统一为浅薄荷蓝渐变、半透明白卡片、细高光、轻阴影和深绿色重点操作。保留原生顶部和底部导航；轻玻璃效果不依赖持续动画或大面积实时模糊。

关注页分别显示关注开关、后台检测、消息发送、微信授权。商品图与标题并排，添加和刷新按钮缩至合适宽度；编辑、暂停关注、删除有明确用途。商品配色图片、容量排序、城市搜索、会员兑换、提醒删除与清空均保留。功能验收页仍不进入微信上传目录，付费购买仍暂停。

## 自动监测实现

- 新增独立云函数 `gxs_monitor`，按分钟触发，关闭小程序后仍由云端运行。
- 复用已有会员/关注筛选、库存状态机、持久事件、消息任务、请求预算和限流退避。
- 一分钟内重复触发不会重复采集；冷启动时的时间抖动不会让正常调度每隔一轮漏扫。
- 调度进度、限流冷却跨调用保存。超过单轮处理能力的门店保留次序，下一轮继续。
- 观测与心跳写入都校验数据库租约，旧执行者失去执行权后不能覆盖新执行者的数据。
- 真实定时来源通过平台内置标记验证；独立函数的客户端调用权限关闭。
- 用户接口增加 `templateConfigured / deliveryReady / reason`，不再用一个开关假定全部能力就绪。

部署、运行日志及真实自动观测证据见 `evidence/verification/1.1.0/`。心跳正常只说明任务在运行；判断数据是否有效还要看对应商品和门店的实际观测、错误和时间。

2026-09-16 09:32、09:33、09:34（北京时间）已验证三个连续的真实定时调用，每轮读取两家门店并保存两条自动观测；天环广场、珠江新城的 `MJYE4CH/A` 均为暂无供应。首轮发现的并发续租事务冲突已修复并重新部署，以上三轮为最终部署后的记录。

## 微信消息仍需管理员配置

用户已确认尚未添加补货订阅模板。因此本版可先运行库存监测，消息发送继续关闭。添加模板、配置消费者 AppID/AppSecret、获得用户主动授权后，才能验证真实微信发送与手机收信。

完整步骤见 [订阅消息配置指引](SUBSCRIBE_SETUP.md)。定时任务部署和停用方式见 [监测部署说明](SCHEDULED_MONITOR.md)。一次性订阅授权不是无限消息额度。

## 验证边界

本次运行完整自动化回归、官方安装版 WXML/WXSS/Babel 编译检查、离线布局与图片检查。浏览器界面读取因安全工具无法可靠识别网址而终止，之后未继续操作桌面界面，因此本次没有声明已完成微信开发者工具页面交互或 iOS/Android 真机验收。

离线页面使用明确标记的样例数据，不调用真实业务，不发送演示补货消息。当前上传源码与实际云端采集是不同部署步骤；更新云函数不会自动替换用户已经发布的小程序界面。
